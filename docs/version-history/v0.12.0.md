## Purpose

Stop the export silently discarding images the user asked for, and settle the v0.11.0 image-model question with live evidence.

## User-visible changes

**Images are no longer dropped by an automatic budget.** The export previously refused any image over 3 MiB, stopped embedding after 12 MiB in total, and capped the count at 64. On a real conversation of ten generated images at roughly 2.5 MB each, that silently discarded three of them behind an `[image unavailable: export exceeds the 12 MiB total embedded image budget]` marker. All three caps are removed.

**The image chooser is now the control.** It gains a `Select all` toggle — tri-state, so it reflects a partial selection rather than lying about it — and a live readout of how many images are selected and how many bytes they will embed. Since nothing is capped any more, that running total is the only signal that a selection will produce an unwieldy file, so it updates on every change and is announced to assistive technology via `aria-live`.

**A throttled download no longer loses an image.** Uncapped exports run longer, so a `429` on either the metadata probe or the image byte fetch is retried once, honouring `Retry-After` clamped to 1-15 seconds. A second `429` is a real failure.

## Image-model finding

The v0.11.0 image-model label was merged without the live test its own record required. That test has now been run, using the bounded probe in `diagnostics/`.

Across ten generated images spanning several weeks and two assistant models, `metadata.dalle` and `metadata.generation` are present on every generated image and absent on user uploads — but neither contains any model identifier. The complete field sets are:

- `dalle`: `edit_op`, `gen_id`, `parent_gen_id`, `prompt`, `seed`, `serialization_title`
- `generation`: `gen_id`, `gen_size`, `gen_size_v2`, `height`, `is_purchasable`, `is_sticker`, `orientation`, `parent_gen_id`, `projection`, `seed`, `serialization_title`, `transparent_background`, `width`

`serialization_title` is a fixed label — identical in length across every image regardless of which assistant model produced it — not an identifier.

`message.metadata.model_slug` and `resolved_model_slug` do hold a real model name, but it is the **assistant** model for the turn, not the image model. Using it would be exactly the inference the feature is required never to make, so it remains unused.

Conclusion: ChatGPT exposes no per-image model identifier, and `Image model: unknown / not found` is the permanent result rather than a gap to be closed. Testing was done on a free-tier account; a paid tier was not checked, though nothing in the schema suggests it differs. What to do about the now-permanently-empty label is an open product decision and is **not** changed in this release.

## Behaviour deliberately unchanged

- Image-model extraction and its `unknown / not found` fallback are untouched, pending that decision.
- `IMAGE_LIMITS` and `applyImageBudget` remain exported and functional. A caller that passes a finite `limits` object still gets budget markers; only the default is now unlimited.
- The per-image omission markers, the same-origin Estuary URL allowlist, and the restrictive offline CSP are unchanged.
