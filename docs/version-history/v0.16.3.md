## Purpose

The product owner's live test of v0.16.2. The ChatGPT dialog controls are visible now.
Two faults remain.

**A Claude chat still fails with a 404, and the report misled.** The report read
"Organizations checked: 2" and listed two requests as Claude's page's:
`…/chat_conversations/<this-chat>?tree,rendering_mode,render_all_tools` and
`…/<this-chat>/composer_notices`. The first is almost certainly the exporter's own
request to the first organization: it has exactly the exporter's query keys, while
Claude's page asks with `tree, rendering_mode, render_all_tools,
include_inline_comparison, consistency` (a DevTools capture published on jvt.me,
2026-09-04). The browser's Resource Timing log holds the exporter's requests next to the
page's, and v0.16.2 did not tell them apart. The stand-in run below shows the same flaw:
v0.16.2 reported the exporter's own `/api/organizations` request as the page's. So the
report held no evidence of how Claude's page loads this chat. All it shows is that the page
asked for its composer notices.

v0.16.3:

- remembers each of its own requests with its time window and leaves them out of the
  report;
- shows each page request's HTTP status where the browser records one (Chromium does);
- always lists the page's other recent requests, including data requests made with fetch
  or XHR outside `/api`;
- says whether the organization Claude's page used was among those checked;
- after a 404 or 403 in every organization the account lists, asks up to three more times,
  each built from evidence:
  1. in the organization Claude's page used for this chat;
  2. with the exact query of the page's own conversation request (a GET, and only when
     that query asks for the message tree the normalizer reads);
  3. with `consistency=strong` added, as Claude's page does.

  A chat that exports on the first request is unaffected.

**Claude exports name one model.** The owner retried one prompt with Haiku, Sonnet and
Opus 5.5. The export's header read `Model: claude-opus-5-5` and every reply read
`Model: unknown / not found`. Opus 5.5 is the chat's own `model` field. No public capture
of Claude's chat API shows a model on a reply, and the exporters we found read only the
chat-level field. v0.16.3:

- reads a model from any field on a reply whose name mentions a model, at most two levels
  down, outside the reply's content, when the value is a Claude model ID;
- names the chat model as such when no reply has one:
  `Chat model: claude-opus-5-5 (Claude’s data names no model for individual replies)`.

Whether Claude records the model per reply at all is unconfirmed;
`diagnostics/claude-reply-model-probe.js` answers it.

## Privacy

Retries are same-origin GETs with the session cookie, like the first request. The
organization comes from the page's own request and must pass the same ID check as the
cookie value. A replayed query has at most eight parameters. Each name and value must match
a short allowlist pattern, and the query must ask for the message tree. The report adds
HTTP statuses and query key names only. Identifiers stay redacted and query values are
dropped. The reply-model scan skips content, text, attachments and files, and accepts only
values shaped like `claude-…`. The probe prints field names, and values only for model
fields that pass a short identifier test.

## Limitations

If the retries fail, the chat still cannot be exported. The new report is meant to show
where Claude's page gets this chat. Per-reply models appear only if Claude's data carries
them.
